# Команды

Расширение регистрирует пять пользовательских команд. Все доступны и в TUI, и в других режимах (rpc, print), но уведомления через `ctx.ui.notify` показываются только в TUI.

## 1. `/billing-status`

**Аргументы:** нет.

**Поведение:**
1. Читает state через `readStateSync()`.
2. Если state отсутствует — `notify("pi-billing-window: state не инициализирован", "info")`.
3. Иначе считает `remain = max(0, windowMs - (now - windowStartedAt))`, форматирует как `HH:MM ч:мин` и показывает: `<provider>: до reset HH:MM ч:мин (calls=N, resets=N)`.

**Сообщения:**
- Успех: `wormsoft: до reset 01:23 ч:мин (calls=42, resets=17)`
- Пусто: `pi-billing-window: state не инициализирован`

**Побочные эффекты:** нет.

## 2. `/billing-tick`

**Аргументы:** нет.

**Поведение:**
1. Обновляет `currentCtx` (чтобы `buildEmitFn()` находил живую шину).
2. Определяет локальный `emit`, который превращает каждый эмит в `ctx.ui.notify("[<event>] <payload-json-truncated>", "info")`.
3. Вызывает `checkAndReset(localEmit)`.
4. Показывает результат: `Тик: reset произошёл` или `Тик: reset не произошёл`.

**Сообщения:**
- Если бы произошёл `billing:window_reset` (но он подавлен дедупом в большинстве случаев): `[billing:window_reset] {"provider":"wormsoft","windowStartedAt":..., ...}`
- Если бы произошёл `billing:window_about_to_reset`: `[billing:window_about_to_reset] {"provider":"wormsoft","msRemaining":12345}`
- Финал: `Тик: reset произошёл` / `Тик: reset не произошёл`

**Использование:** отладка без ожидания 5-минутного интервала.

**Побочные эффекты:** возможен реальный reset (если дедуп не сработает) — это **изменит** `windowStartedAt`, `resetCount`, обнулит `callsInWindow`.

## 3. `/billing-reset`

**Аргументы:** нет.

**Поведение:**
1. `mutateState`: `resetCount++`, `windowStartedAt = now`, `lastResetAt = now`, `callsInWindow = 0`, `firstCallEmittedAt = undefined`.
2. `notify("Окно сброшено вручную", "info")`.
3. Если `ctx.mode === "tui"` — `forceUpdateStatus(ctx)` (обновить футер немедленно).
4. Если есть `bus` — эмитит `billing:window_reset` со свежим state.

**Сообщения:**
- Успех: `Окно сброшено вручную`
- (через шину): `billing:window_reset` со свежим state, а также `handleWindowReset` нарисует «wormsoft: 2-часовой лимит сброшен…» в TUI.

**Побочные эффекты:** сброс окна (см. таблицу в [`STATE.md`](./STATE.md)).

## 4. `/settimer <duration>`

**Аргумент:** строка длительности.

**Поддерживаемые форматы:**

| Формат | Пример | Интерпретация |
|---|---|---|
| `N` (целое) | `60` | N минут |
| `Nm` | `90m` | N минут |
| `Nh` | `2h` | N часов |
| `Nh Nm` | `1h30m` | N часов и M минут |

Допускаются пробелы между частями: `1 h 30 m`. Регистр не важен.

**Не поддерживается:** `Ns`, `Nd`, дробные числа (`1.5`), отрицательные значения, мусор.

**Поведение (два разных сценария):**

1. Парсит аргумент через `parseDuration(arg)`.
2. Если ошибка — `notify("Неверный формат: '<arg>'. Примеры: 60, 1h30m, 0", "error")`.
3. Если пустой аргумент — `notify(usage, "info")`.
4. Clamp: `durationMs = min(max(0, parsed.totalMs), windowMs)`.

**`durationMs = 0` — немедленный reset** (зеркалит `/billing-reset`):
1. `mutateState`: `windowStartedAt = now`, `lastResetAt = now`, `resetCount++`, `callsInWindow = 0`, `firstCallEmittedAt = undefined`.
2. Эмитит `billing:window_reset` со свежим state **напрямую** (в обход `checkAndReset`, чей дедуп подавил бы событие — `lastResetAt` только что обновлён).
3. `notify("Таймер: окно сброшено (свежие 2 часа)", "info")`.

**`durationMs > 0` — синхронизация отсчёта** (с личным кабинетом wormsoft):
1. Пересчитывает `windowStartedAt = now - (windowMs - durationMs)`.
2. `mutateState`: новый `windowStartedAt`, `resetCount++`, `callsInWindow = 0`, `firstCallEmittedAt = undefined`. **`lastResetAt` не трогается** — иначе дедуп `checkAndReset` подавил бы будущий авто-reset на границе окна.
3. Эмита нет (reset ещё не произошёл).
4. `notify("Таймер установлен: HH:MM:SS до reset", "info")`.
5. Если TUI — `forceUpdateStatus(ctx)`.

**Сообщения:**

| Кейс | Текст |
|---|---|
| Пустой аргумент | `Использование: /settimer <длительность>\nПримеры: /settimer 60, /settimer 1h30m, /settimer 0 (сброс)` |
| Неверный формат | `Неверный формат: '<arg>'. Примеры: 60, 1h30m, 0` |
| Отрицательное | `Неверный формат: '<arg>'. Примеры: 60, 1h30m, 0` (из парсера, подсказка: «отрицательное значение недопустимо») |
| Дробное | (подсказка парсера: «дробные значения не поддерживаются») |
| `60s` / `1d` | (подсказка парсера: «секунды/дни не поддерживаются, используйте минуты или часы») |
| Успех (duration > 0) | `Таймер установлен: 00:01:30 до reset` |
| Успех (`/settimer 0`) | `Таймер: окно сброшено (свежие 2 часа)` |

**Примеры:**

```text
/settimer 96          → 96 мин до reset (1 ч 36 мин)
/settimer 1h30m       → 1 ч 30 мин до reset
/settimer 2h          → 2 ч до reset (= длине окна; фактически «только что начали»)
/settimer 0           → немедленный reset + emit billing:window_reset
/settimer 10h         → clamp до 2 ч (WINDOW_MS), результат как /settimer 2h
/settimer abc         → ошибка формата
/settimer 90s         → ошибка: «секунды не поддерживаются»
```

**Побочные эффекты:** при `duration > 0` — синхронизация отсчёта (окно передвинуто, счётчики обнулены, `lastResetAt` не тронут); при `0` — полный reset с emit.

## 5. `/cont-after-reset [N|off]`

**Аргументы:** нет (взвести одноразово) | `N` (целое 1..99 — взвести на N срабатываний) | `off` (снять; также принимаются `0`, `нет`, `выкл`).

**Назначение:** автопродолжение прерванной задачи. Когда 2-часовое окно сбросится, расширение само отправит в чат слово `продолжи` — задача, остановленная вручную или по исчерпанию токенов wormsoft, возобновится. Без аргумента флаг одноразовый; с числовым аргументом `N` — на N срабатываний: после каждого подтверждённого продолжения флаг перевзводится, пока счётчик не исчерпается (ночная автономная работа переживает несколько 2-часовых окон).

**Поведение при взводе (без аргумента или с `N`):**
1. `armsSwitchKey(sessionKeyOf(ctx))` — привязка к файлу текущей сессии.
2. Читает state. Без аргумента — идемпотентно: берёт существующий активный флаг либо взводит новый через `armsArm(lastResetAt)`. С явным `N` — сначала снимает активный флаг и взводит новый через `armsArm(lastResetAt, now, N)`. В обоих случаях фиксируется `lastResetAt` на момент взвода, чтобы сработал только сброс, случившийся ПОСЛЕ взвода.
3. Запускает armed-poller (опрос каждые 10 с) + boundary-таймер на точную границу окна (чтобы не ждать 5-минутного тика).
4. `notify(...)` с расчётным моментом срабатывания и сроком годности.
5. Если TUI — в футере к таймеру добавляется маркер `[cont-after-reset]`.

**Поведение при `off`:** `armsDisarm()` + остановка poller'а; `notify("cont-after-reset: флаг снят")` (или «флаг не был взведён»).

**Как срабатывает (см. [`ARCHITECTURE.md`](./ARCHITECTURE.md) §5.1):** poller каждые 10 с проверяет `resetReadyToFire(arm, state, now)` — `state.lastResetAt` продвинулся относительно `arm.lastResetAtAtArm` **и** прошло ≥ 60 с grace (чтобы wormsoft успел вернуть токены). Если агент в этот момент стримит (`ctx.isIdle() === false`) — ждём, повтор на следующем опросе. После успешной отправки `продолжи` (`pi.sendUserMessage`) флаг переходит в фазу `pending` (не снимается сразу): при 429 от провайдера отправка повторяется не чаще раза в 10 мин (`RETRY_AFTER_FIRE_MS`), а первый успешный ответ (`confirmSuccess`) разрешает флаг — одноразовый удаляется; при `repeat > 1` запись перевзводится (`repeat - 1`, `phase = "armed"`, `lastResetAtAtArm` = последний сброс, новый TTL 8 ч) и сработает на следующем сбросе.

**Сообщения:**

| Кейс | Текст |
|---|---|
| Взведён | `cont-after-reset: взведён, сработает при сбросе окна (через ~N мин). Режим повтора: N срабатываний всего (repeat=N). Срок годности флага: до HH:MM:SS (N мин) — если сброса не будет, флаг сгорит.` (для одноразового — фрагмент `Одноразовый флаг.`) |
| Снят | `cont-after-reset: флаг снят` |
| Не был взведён | `cont-after-reset: флаг не был взведён` |
| Ошибка взвода | `cont-after-reset: не удалось взвести флаг` |

**Побочные эффекты:** запись в `~/.pi/agent/pi-billing-window-arms.json` (см. [`STATE.md`](./STATE.md) §8); флаг переживает `/new` (переносится на новую сессию окна) и перезапуск процесса (пере-усыновляется по файлу сессии). TTL флага — 8 часов от взвода (при repeat-перевзводе отсчитывается заново).

## 6. Общие соглашения
- Все команды **не должны** ронять pi. Любая ошибка ловится и показывается через `notify`.
- Команды идемпотентны там, где это осмысленно: `/billing-status` (чтение), `/billing-tick` (с дедупом), `/cont-after-reset` (повторный взвод не перезаписывает активный флаг). `/billing-reset`, `/settimer` — **изменяющие** (state + emit событий).
- Если `ctx.ui.notify` отсутствует (rpc-режим) — все уведомления молча проглатываются. Это намеренно: в headless-режиме мы не хотим засорять лог.

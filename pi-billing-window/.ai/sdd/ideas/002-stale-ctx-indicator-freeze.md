# Idea: Замороженный индикатор окна в долго живущих TUI-окнах (stale ctx + тихие отказы)

> Status: idea:captured
> Created: 2026-11-02
> Source: расследование инцидента 2026-11-02 (оркестратор), директива пользователя в чате

## Raw Idea

Индикатор `[обновится в ЧЧ:ММ]` в футере замёрз минимум на 8 минут после reset,
хотя reset-механика (watchdog, state, re-anchor) отработала корректно, а
живой RPC-тест в свежем процессе показывает корректный setStatus. Виджет
умирает тихо: каждое обновление статуса (тик 30 с и событийные пути) либо
молча bail'ит, либо молча ловит исключение устаревшего ctx — и никогда не
перепривязывается. Направление: диагностика отказов обновления виджета
(JSON-lines лог) + самопочинка — подмена устаревшего ctx апдейтера свежим
ctx из событий (session_start / model_select / after_provider_response) +
гарантия, что косметика статуса никогда не рвёт событийные цепочки
(напр. checkAndReset после after_provider_response).

## Problem Space

- **Problem:** тихие отказы обновления статус-виджета в долго живущих TUI-
  окнах после session replacement/reload; нулевая диагностика — после
  инцидента невозможно установить, какой путь отказал.
- **Who:** пользователь с несколькими окнами pi на wormsoft; ночные автономные
  сессии, где индикатор — единственный видимый сигнал границы окна.
- **When:** после /settimer и последующего session replacement/reload в том же
  окне; воспроизводится не в свежем процессе (живой ctx).
- **Workaround:** перезапуск окна pi (неизвестен пользователю — симптом
  «индикатор врёт», а не «расширение умерло»).

## Desired Outcome

1. Любой отказ обновления виджета оставляет след в
   `~/.pi/agent/pi-billing-window-uidiag.log` (JSON-lines, rate-limited).
2. Устаревший ctx апдейтера подменяется свежим при первом же событии
   (ответ LLM, смена модели, session_start) — виджет сам оживает без
   перезапуска окна.
3. Ошибка косметики статуса не может оборвать `checkAndReset` в
   after_provider_response и другие событийные цепочки.

## Signals of Value

- Инцидент-репродукция: два окна, /settimer → после reset оба показывают
  новую границу без перезапуска; uidiag-лог показывает путь и причину.
- Ночные сессии: индикатор согласован с state после каждого ответа LLM.

## Constraints

| Constraint | Notes |
|---|---|
| Пассивность | расширение никогда не роняет host-процесс (NFR проекта) |
| Стоимость | диагностика только на отказах; тик 30 с остаётся дешёвым |
| Два окна | один общий uidiag-файл, append из разных процессов |
| Тесты | стиль tests/test.mts (assert, harness, инъекция путей) |

## Possible Directions

- **A. Диагностика + самопочинка через события** (выбрано, user-approved):
  applyStatus возвращает код исхода; uidiag-лог; `refreshStatusContext(ctx)`
  из index.ts; небросающий forceUpdate; счётчик неудач тика (Should).
- **B. Перепривязка ctx прямо в тике** — отклонено: тику неоткуда взять
  свежий ctx (module state не знает о новых событиях), это лечит симптом.
- **C. Полный отказ от module-level currentCtx, обновление только из событий**
  — отклонено: тик 30 с нужен как страховка (дешёвый, читает один state-файл).

## Resolved Questions (контекст для requirements)

- Reset сработал вовремя (14:08:46, watchdog, state корректен), ре-якорь
  firstCall 14:14:51 → граница 16:14; замерли только индикаторы обоих окон.
- Живой RPC-тест в свежем процессе: setStatus приходит корректный — путь
  setStatus/ui.ts жив; деградация специфична для долго живущих процессов.
- Найденные классы дефектов: (1) тик молча ловит throw устаревшего ctx
  навсегда, без перепривязки; (2) молчаливые bail-ветки applyStatus;
  (3) handleWindowReset/refreshMarker — тихий ранний return на stale ctx;
  (4) onAfterProviderResponse: `ctx.mode === "tui"` + forceUpdateStatus без
  защиты — исключение косметики убивает `checkAndReset` в хвосте обработчика;
  (5) нулевая пост-мортем-наблюдаемость.

## Overview

Индикатор `[обновится в ЧЧ:ММ]` (ui.ts: тик 30 с через `ctx.ui.setStatus` +
точечные обновления из index.ts) замёрз в двух долго живущих TUI-окнах на
8+ минут после корректного reset'а. Reset-механика жива (watchdog, state,
re-anchor), setStatus в свежем RPC-процессе работает — деградация
специфична для долго живущих процессов и происходит ТИХО:

1. **Тик навсегда мёртв:** `startStatusUpdater` (ui.ts ~168-185) ловит throw
   устаревшего ctx (getter `ctx.ui`/`ctx.mode` бросает через assertActive
   после session replacement/reload) и `return` — каждый тик молча падает,
   ctx никогда не перепривязывается, диагностики нет.
2. **Молчаливые bail-ветки applyStatus** (ui.ts ~69-97): нет ctx.ui /
   provider != wormsoft / нет state — без следа.
3. **Тихий ранний return на stale ctx** в событийных путях index.ts:
   `handleWindowReset` (~2185, `ctxIsTui` глотает throw → без notify, без
   refresh, без лога), `refreshMarker` (~993).
4. **Незащищённая косметика рвёт логику:** `onAfterProviderResponse`
   (~2872): `if (ctx.mode === "tui") forceUpdateStatus(ctx)` без try/catch —
   исключение статуса убивает обработчик ДО `await checkAndReset(...)` в его
   хвосте: косметика ломает reset-логику.
5. **Нулевая пост-мортем-наблюдаемость:** после инцидента невозможно
   установить, какой именно путь отказал.

Фича: (а) каждый отказ обновления виджета оставляет JSON-lines след;
(б) устаревший ctx апдейтера подменяется свежим при первом же событии;
(в) обновления статуса из обработчиков никогда не бросают; (г) счётчик
неудач тика (Should) — интервал продолжает тикать и оживает после подмены.

## Business Context

- **Problem:** тихая смерть индикатора окна в долго живущих окнах; симптом
  для пользователя — «индикатор врёт», реальная причина невидима.
- **Users:** пользователь с несколькими окнами pi на wormsoft; ночные
  автономные сессии (индикатор — единственный видимый сигнал границы).
- **Value:** виджет самовосстанавливается без перезапуска окна; любой отказ
  диагноструем пост-фактум по лог-файлу; reset-логика не зависит от
  косметики статуса.
- **Success signal:** инцидент-репродукция (два окна, /settimer) — оба
  индикатора показывают новую границу без перезапуска; uidiag-лог
  идентифицирует путь и причину отказа.

## Goals

- Каждый отказ обновления статус-виджета логируется (JSON-lines, rate-limited).
- Устаревший ctx апдейтера подменяется свежим живым ctx при первом же
  событии (session_start, model_select, after_provider_response) и статус
  применяется немедленно.
- Обновление статуса из любого обработчика событий не бросает — цепочки
  (в т.ч. `checkAndReset` после after_provider_response) не рвутся.
- Интервал тика продолжает работать при сбоях; подмена ctx его оживляет.

## Non-Goals / Out of Scope

- Изменение reset-механики, watchdog, wake-таблицы, state-схемы — untouched.
- Изменение формата/визуала виджета (`[обновится в ЧЧ:ММ]`) и правила
  видимости (только wormsoft) — untouched.
- Перепривязка ctx прямо внутри тика (направление B, отклонено — см. idea 002).
- Логирование успешных обновлений (только отказы — NFR-018-2).
- Замена module-level currentCtx на архитектуру «только события»
  (направление C, отклонено — тик нужен как дешёвая страховка).

## User Stories

### US-018-1: самопочинка виджета

**Как** пользователь, работающий в долго живущем окне pi,
**я хочу** чтобы после session replacement/reload индикатор сам показывал
актуальную границу при первом же ответе LLM (смене модели, session_start),
**чтобы** не перезапускать окно и не сомневаться в таймере.

**Acceptance Criteria:**
- [ ] Устаревший ctx апдейтера подменяется живым ctx из события; статус
      применяется в том же вызове.
- [ ] Следующий тик использует новый ctx.

### US-018-2: пост-мортем диагностика

**Как** разработчик расширения, разбирающий инцидент «индикатор замёрз»,
**я хочу** лог отказов обновления виджета с причиной и путём,
**чтобы** за один просмотр файла установить, какой путь отказал и когда.

**Acceptance Criteria:**
- [ ] Отказ оставляет JSON-строку {ts, pid, reason, detail} в
      `~/.pi/agent/pi-billing-window-uidiag.log`.
- [ ] Повторяющийся отказ не заливает лог (rate-limit), файл не растёт
      бесконечно (кап).

### US-018-3: косметика не рвёт логику

**Как** пользователь ночной автономной сессии,
**я хочу** чтобы ошибка обновления статус-строки не мешала reset'у окна,
**чтобы** `checkAndReset` в хвосте after_provider_response выполнялся всегда.

**Acceptance Criteria:**
- [ ] forceUpdate и обёртки обновления из обработчиков не бросают.
- [ ] Порядок after_provider_response: обновление статуса не прерывает
      последующий checkAndReset.

## Functional Requirements

Нумерация FR-018-N. Приоритет Must, если не указано иное.

### FR-018-1 (Must) — applyStatus возвращает код исхода

THE SYSTEM SHALL изменить `applyStatus(ctx, key, provider?)` (ui.ts ~69-97)
так, чтобы она возвращала код исхода:
`"ok" | "cleared" | "bail:no-ctx" | "bail:no-ui" | "bail:provider" |
"bail:no-state" | "error"`, WHERE bail-коды соответствуют существующим
тихим ветвям (нет ctx/ctx.ui; provider != wormsoft; нет state), "ok" =
текст установлен, "cleared" = строка снята setStatus(key, undefined),
"error" = обращение к ctx бросило (stale ctx), SO THAT каждый вызывающий
путь получает машинно-читаемую причину для диагностики (FR-018-2) и
управляющей логики (FR-018-3, FR-018-6).

### FR-018-2 (Must) — uidiag: JSON-lines диагностика отказов обновления виджета [FR-A]

WHEN любой путь обновления статус-виджета отказывает (исключение при
обращении к ctx ИЛИ тихий ранний return из-за мёртвого ctx в событийном
обработчике), THE SYSTEM SHALL добавить одну JSON-строку в
`~/.pi/agent/pi-billing-window-uidiag.log` формата
`{"ts":"<ISO8601>","pid":<number>,"reason":"<путь:причина>","detail":"<строка, ≤200 символов>"}`,
WITH rate-limit: не более одной строки на reason-эпизод на процесс
(эпизод = подряд идущие события одного reason; смена reason начинает новый
эпизод), WITH кап: при превышении 400 строк файл обрезается до последних
200, SO THAT пост-мортем инцидента сводится к чтению одного маленького
файла, а лог не растёт бесконечно и не заливается повторами.
IF запись в файл сама падает (нет прав, диск), THE SYSTEM SHALL молча
проглотить ошибку SO THAT диагностика никогда не роняет host-процесс.

### FR-018-3 (Must) — refreshStatusContext: подмена устаревшего ctx апдейтера [FR-B]

THE SYSTEM SHALL добавить экспорт `refreshStatusContext(ctx, provider?)`
в ui.ts: IF ctx жив (чтение `ctx.mode === "tui"` не бросает и даёт true) и
ctx отличен от текущего `currentCtx` апдейтера, THE SYSTEM SHALL подменить
`currentCtx := ctx` и немедленно применить статус (applyStatus с
переданным provider); IF ctx === currentCtx, THE SYSTEM SHALL просто
применить статус (идемпотентно); IF ctx мёртв (чтение mode бросает) или
не tui, THE SYSTEM SHALL тихо вернуться (мёртвый ctx — с записью
FR-018-2), SO THAT устаревший апдейтер оживает при первом же событии
без перезапуска окна и без остановки/перезапуска интервала.

### FR-018-4 (Must) — точки самопочинки в index.ts [FR-B]

THE SYSTEM SHALL вызывать `refreshStatusContext(ctx)` из index.ts в:
(a) `onAfterProviderResponse`-хвост (~2872) — вместо незащищённого
`if (ctx.mode === "tui") forceUpdateStatus(ctx)`;
(b) `onModelSelect` (~2890) — с `event?.model?.provider` как provider;
(c) `onSessionStart` (~2563, сразу после `stopStatusFn = startStatusUpdater(ctx)`),
SO THAT каждый ответ LLM, смена модели и старт сессии чинят/подтверждают
привязку апдейтера к живому ctx.

### FR-018-5 (Must) — обновления статуса из обработчиков не бросают [FR-C]

THE SYSTEM SHALL гарантировать, что `forceUpdate` (ui.ts) и все вызовы
обновления статуса из обработчиков событий index.ts не бросают:
(a) `forceUpdate` оборачивает applyStatus и при исключении возвращает
"error" с записью FR-018-2 (reason вида `force:error`);
(b) `handleWindowReset` (~2185): stale-ctx (чтение mode бросает) → тихий
ранний return ЗАМЕНЯЕТСЯ на диагностику reason `window-reset:stale-ctx`
(non-tui процесс — по-прежнему тихо, это норма);
(c) `refreshMarker` (~993) — аналогично `marker:stale-ctx`;
(d) `onAfterProviderResponse`: сравнение `ctx.mode === "tui"` (~2872)
заменяется на безопасную проверку (не бросает на stale ctx),
SO THAT исключение косметики статуса не прерывает `await checkAndReset(...)`
и другие последующие шаги обработчиков.

### FR-018-6 (Should) — счётчик подряд идущих неудач тика [FR-D]

THE SYSTEM SHALL в тике апдейтера (ui.ts, setInterval в
startStatusUpdater) считать подряд идущие неудачные тики (исход "error");
первая ошибка эпизода (streak === 1) записывается через FR-018-2
(reason `tick:error`), последующие — только инкремент счётчика; успешный
тике сбрасывает счётчик в 0; THE SYSTEM SHALL продолжать тикать при
неудачах (стоимость тика мала) SO THAT подмена ctx через FR-018-3
оживляет виджет ближайшим тиком, а эпизод тихой смерти виден в логе
одной строкой.

## Non-Functional Requirements

### NFR-018-1: пассивность

- Ни один новый путь (uidiag, refreshStatusContext, счётчик) не бросает
  наружу; все fs-операции uidiag — в try/catch; расширение никогда не
  роняет host-процесс (инвариант проекта, spec 007).

### NFR-018-2: уномитарная стоимость

- uidiag пишется ТОЛЬКО на отказах; успешные обновления не логируются.
- Rate-limit (1 строка на reason-эпизод) и кап (>400 → 200) гарантируют
  размер файла ≤ десятков КБ.
- Тик остаётся прежним (30 с, один readStateSync); новые таймеры не вводятся.

### NFR-018-3: не блокирующие операции

- uidiag — appendFileSync одной короткой строки (≤ ~200 байт) при
  отказе (редко); кап-обрезка — редкая синхронная перезапись маленького
  файла. Никаких async-очередей и фоновых таймеров диагностики.

### NFR-018-4: тесты

- Юнит-тесты — в tests/test.mts (стиль существующих: assert-хелпер,
  mkdtempSync tmpdir, инъекция путей через set*Paths, мок-ctx).

### NFR-018-5: exit hygiene

- Новых таймеров нет; существующий interval уже unref (spec 003) —
  счётчик ошибок не влияет на refs.

## Constraints

- Реализация без сборки: TypeScript/tsx, деплой копированием .ts
  (deploy.ps1) — без новых зависимостей.
- uidiag-файл общий для всех процессов/окон pi на машине: строки от разных
  pid чередуются; append одной строки атомарностью уровня ОС достаточен
  (строка короткая; потеря строки в race — приемлема, это best-effort лог).
- Минимальный diff в index.ts: не трогать reset-механику, watchdog,
  wake-таблицу.

## Decisions (направление утверждено пользователем в чате; детализация — оркестратор)

### D-001: applyStatus → код исхода
Каждая тихая ветвь и исключение получают машинный код; коды — единый
источник причин для uidiag, тестов и счётчика. Impacts: FR-018-1.

### D-002: uidiag — отдельный модуль src/uidiag.ts
Не функции в ui.ts: (а) инъекция пути для тестов без вмешательства в
module-state ui.ts; (б) одна ответственность — лог; (в) ui.ts остаётся
только про виджет. Экспорты: `uidiag(reason, detail?)`,
`setUidiagPathForTests()`, `resetUidiagPathForTests()`. Impacts: FR-018-2.

### D-003: rate-limit семантика — reason-эпизод
Эпизод = подряд идущие записи одного reason в жизни процесса; повтор
того же reason после другого reason логируется заново. Проще TTL-таймеров,
достаточно против залива. Impacts: FR-018-2, NFR-018-2.

### D-004: forceUpdate небросающий внутри ui.ts
Не обёртки в каждом месте index.ts (9 точек вызова forceUpdateStatus),
а один безопасный forceUpdate в ui.ts: все точки защищены разом,
сигнатура не меняется, возврат — код исхода. Impacts: FR-018-5.

### D-005: тик никогда не перепривязывает ctx сам
Тику неоткуда взять свежий ctx (module state); самопочинка — только
явная, из событий с живым ctx (FR-018-3/4). Тик остаётся дешёвым зондом
(FR-018-6). Impacts: FR-018-3, FR-018-6.

### D-006: диагностика только ошибок ctx-доступа
bail:no-ctx / bail:no-ui / bail:provider / bail:no-state — нормальные
ветки (до старта апдейтера, не-tui, чужой провайдер, окно ещё не создано) —
не логируются; uidiag — только "error" (stale ctx) и stale-ранние-return'ы
событийных путей. Иначе лог зашумляется на каждый переключение модели.
Impacts: FR-018-2, NFR-018-2.

## Questions (закрытые — отвечены расследованием/директивой)

### Q-1: почему reset сработал, а индикатор — нет? (answered)
Reset идёт через watchdog/state (не зависит от ctx TUI); виджет зависит от
ctx.ui — после session replacement ctx мёртв, каждый тик тихо падает.
Решение оркестратора: самопочинка через события (FR-018-3/4).

### Q-2: почему свежий RPC-процесс показывал корректный setStatus? (answered)
В свежем процессе ctx жив; деградация специфична для долго живущих окон
со stale ctx. Подтверждает, что путь setStatus/ui.ts исправен, лечить
нужно привязку ctx. Решение: FR-018-3.

### Q-3: логировать ли успешные обновления? (answered)
Нет — только отказы (D-006, NFR-018-2).

### Q-4: атомарность uidiag при двух окнах? (answered)
appendFileSync одной короткой строки достаточен (best-effort лог, pid в
строке различает окна); loss строки в race приемлем. Решение оркестратора.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| uidiag-файл недоступен (права/диск) | всё в try/catch, молча (FR-018-2, NFR-018-1) |
| Два окна append в race | короткая строка + pid; loss приемлем (Constraints) |
| Лог заливается повторами | эпизодный rate-limit + кап (D-003) |
| refreshStatusContext с мёртвым ctx | безопасная проверка mode + тихий return с diag (FR-018-3) |
| Регресс событийных обработчиков | все существующие сьюты + live-RPC проба (tasks T5) |

## Glossary

- **Stale ctx:** ExtensionContext сессии, заменённой (replacement/reload);
  getters (`ctx.ui`, `ctx.mode`, `ctx.model`) бросают через assertActive.
- **Эпизод (reason-эпизод):** подряд идущие события одного reason в жизни
  процесса; rate-limit uidiag.
- **Апдейтер:** тик startStatusUpdater + его module-state (currentCtx,
  currentKey, currentInterval) в ui.ts.
- **Самопочинка:** подмена currentCtx живым ctx из события +
  немедленное применение статуса.

# Spec 019 — ночной дозор, самовосстановление проверочного запроса, предстарт ночи

## Header

- **Status:** requirements:approved (разбор инцидента утверждён пользователем 2026-11-11 — «составь план исправления и приступи»)
- **Spec ID:** 019-night-sentry-ping-heal
- **Источники:** инцидент ночи 2026-11-10→11 (DevRepoProxy night003):
  `~/.pi/agent/pi-billing-window-arms.log` (строки 1474–1523),
  `~/.pi/agent/pi-billing-window-history.csv` (ночь 10–11.11),
  jsonl сессии `2026-11-10T19-34-51-551Z_01a1c6f4…` (четыре 429 в 19:38Z),
  `~/.pi/agent/pi-billing-window.json` (state.ping: model=openai/gpt-oss:20b, infraStreak=23, HTTP 404),
  `~/.pi/agent/models.json` (у провайдера wormsoft модели gpt-oss больше нет),

  specs 011/012/014/015/017.

## Problem

Ночной прогон DevRepoProxy (10→11.11) погиб через 4 минуты после старта
(четыре 429 подряд в 22:38 лок.) и до утра не возобновился. Ночью не было
отправлено ни одного «продолжи». Четыре независимых разрыва:

1. **D1 — ночь без страховки, и никто не предупредил.** Дневной взвод
   cont-after-reset исчерпал бюджет в 19:10 (arm-gone kind=confirmed-exhausted).
   Ночная сессия стартовала в 22:34 с armed=false. Ни при старте ночной
   сессии, ни в момент исчерпания взвода пользователь не получил никакого
   сигнала «ночь останется без автопродолжения». (Предыдущий инцидент
   24.10.2026 — тот же класс: вечерний disarm, ночь без флага, утреннее
   «почему не работало».)
2. **D2 — мёртвая модель проверочного запроса.** Boundary-пинг (spec 017)
   настроен на модель `openai/gpt-oss:20b`; провайдер её больше не выдаёт —
   все wake-пинги возвращают HTTP 404 (23 подряд за ночь), reset деградировал
   до «слепого». Заложенный в дизайн D-002 откат на запасную модель не
   срабатывает: код классифицирует 404 как infra (сеть), а не как ошибку
   модели. Никакой эскалации после N подряд 404 нет — только одна тихая
   пометка infraNotified в state.
3. **D3 — нет предстарта ночи.** Перед запуском ночного прогона невозможно
   одной командой увидеть: остаток окна (вызовы/время до сброса), состояние
   взвода, активность плана ночи, живость проверочной модели. Прогон был
   запущен в наполовину сгоревшем окне (вечерние работы других проектов
   съели общий лимит) — и об этом тоже никто не предупредил.
4. **D4 — протухший план ночи.** `pi-billing-window-nightplan.json` остался
   от ночи 31.10 (другой проект, expiresAt давно прошёл) и не убирается;
   диагностика «плана нет, но файл есть» не показывается.

## User Stories

- **US-019-1:** Как пользователь, запускающий ночной прогон, я хочу получать
  оповещение, когда ночью идут вызовы модели, а страховки автопродолжения нет
  (и план ночи не активен), чтобы узнать о незастрахованной ночи до того,
  как сессия умрёт от лимита, а не утром.
- **US-019-2:** Как пользователь, я хочу получать оповещение при исчерпании
  взвода (repeat исчерпан / срок истёк) в ночном интервале или незадолго до
  него, чтобы успеть перевзвести флаг или зарегистрировать план ночи.
- **US-019-3:** Как пользователь, я хочу, чтобы проверочный запрос на границе
  окна сам переходил на живую модель провайдера при ошибке «модель не найдена»
  (HTTP 404), чтобы сбросы окна оставались верифицированными, а не слепыми.
- **US-019-4:** Как пользователь, я хочу одной командой видеть предстартовую
  сводку ночи (остаток окна, взвод, план, здоровье проверочного запроса),
  чтобы не запускать прогон в сгоревшем окне и без страховки.
- **US-019-5:** Как сопровождающий, я хочу, чтобы протухший файл плана ночи
  убирался, а не лежал мусором, вводящим в заблуждение при диагностике.

## Functional Requirements

### FR-019-1 (D1, Must) — дозор «ночь без страховки»

WHEN поступает сигнал активности модели ночью (первый вызов окна
`llm:first_call` ИЛИ любой вызов в ночном интервале), AND текущее локальное
время попадает в ночной интервал (по умолчанию 22:00–08:00; приоритет —
интервал активного плана ночи, если задан), AND взвод cont-after-reset
отсутствует (arms.json пуст/TTL истёк), AND активный план ночи отсутствует,
THE SYSTEM SHALL отправить оповещение (notifier + строка состояния) с
текстом вида «ночь идёт без автопродолжения — взведи /cont-after-reset N
или /night-plan», SO THAT пользователь узнаёт о разрыве до гибели сессии,
с дедупликацией: не чаще одного оповещения на календарный час (состояние
дедупа — в state.json, переживает перезапуск).

### FR-019-2 (D1, Must) — сигнал при исчерпании взвода

WHEN sync-путь фиксирует arm-gone (kind=confirmed-exhausted или TTL) в
ночном интервале ИЛИ в течение 2 часов до его начала, THE SYSTEM SHALL
отправить отдельное оповещение «страховка исчерпана до ночи — перевзведи
или зарегистрируй план» (дедуп — один раз на событие arm-gone; не глушить
существующий notify spec 011, а дополнять ночным контекстом).

### FR-019-3 (D2, Must) — самовосстановление проверочного запроса

WHEN boundary-пинг получает HTTP 404 (или 400 с указанием на модель) от
провайдера, THE SYSTEM SHALL классифицировать это как ошибку модели (не
infra), однократно повторить запрос на самую дешёвую модель из актуального
списка моделей провайдера в `~/.pi/agent/models.json` (выбор по
cost.input, при равенстве — по cost.output) и сохранить выбранную модель в
`state.ping.model`, SO THAT ночные сбросы остаются верифицированными без
ручной правки конфигурации. Если в списке провайдера нет ни одной модели —
оставить классификацию infra (сеть) и перейти к FR-019-4.

### FR-019-4 (D2, Must) — эскалация серии отказов проверочного запроса

WHEN infraStreak проверочного запроса достигает порога 10 подряд, THE
SYSTEM SHALL отправить оповещение «проверочный запрос окна не работает
N раз подряд — сбросы слепые» с деталем последней ошибки, с повтором не
чаще одного раза в 6 часов, пока серия не прервётся успехом.

### FR-019-5 (D3, Must) — команда предстарта ночи

WHEN пользователь выполняет `/night-check`, THE SYSTEM SHALL вывести
сводку: (a) окно — вызовов в окне, израсходованные токены, время до сброса
или «окно не начато»; (b) взвод — есть/нет, repeat-остаток, срок, владелец;
(c) план ночи — активен (интервал, repeat) / истёк (файл-мусор) / отсутствует;
(d) проверочный запрос — последняя модель, статус, длина серии отказов;
(e) вердикт: «можно запускать ночь» / список конкретных разрывов (нет
страховки, окно на исходе <30 мин или >80% израсходовано, модель пинга
мертва, план протух). Никакого I/O вне чтения state/arms/plan/models —
сводка не пишет состояние (кроме дедупа оповещений).

### FR-019-6 (D4, Should) — уборка протухшего плана

WHEN план ночи читается и его expiresAt в прошлом, THE SYSTEM SHALL
возвращать «нет активного плана» и при первом таком чтении удалить файл
плана (под лок), с одной пометкой в журнал armslog «nightplan expired,
файл удалён», SO THAT протухшие файлы не копятся и не сбивают диагностику.

## NFR

- **NFR-019-1:** Все новые пути — passive observer: ни одна ошибка не
  роняет host-процесс; таймеры unref (паттерн spec 003/014).
- **NFR-019-2:** Чистые функции (интервальная математика, предикаты дозора,
  сборка сводки) — без I/O, покрытие юнит-тестами ≥25 кейсов; I/O только
  через существующие state.ts/arms.ts/nightplan.ts обёртки.
- **NFR-019-3:** Ни одно оповещение не блокирующее: notifier fire-and-forget.
- **NFR-019-4:** Дедуп-состояние в state.json (мутации через mutateState),
  переживает перезапуск процесса.

## Out of scope

- Изменение механики доставки «продолжи» (specs 007/009/010) — не трогаем.
- Изменение формата ledger/утреннего отчёта (spec 014) — только чтение.
- Автоматический взвод флага без ведома пользователя — запрещено (только
  предупреждения; взвод/план — явное действие человека).
- Лечение лицензионных/инструментальных проблем самого ночного прогона
  DevRepoProxy (Vanessa и пр.) — вне этого расширения.

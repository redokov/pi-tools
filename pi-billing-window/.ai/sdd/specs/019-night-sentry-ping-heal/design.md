# Design: Spec 019 — ночной дозор, самовосстановление проверочного запроса, предстарт ночи

> Requirements: @requirements.md
> Status: approved
> Last Updated: 2026-11-11

## 1. Executive Summary

Четыре точечных добавления без изменения существующей механики доставки:

1. **`src/nightsentry.ts`** (новый, паттерн nightplan.ts) — чистые функции:
   ночная интервальная математика (реэкспорт/дубль логики wrap-полночи),
   предикаты дозора (`nightGap`), сборка сводки `/night-check`
   (`buildNightCheckReport`), дедуп-помощники. Без I/O.
2. **Дозор в `src/index.ts`**: два крючка — (a) на `after_provider_response`
   (точка, где уже известен project/session и открыт state) проверяем
   «ночь + нет arm + нет плана» → оповещение с дедупом 1/час;
   (b) в существующем arm-gone-переходе (sync-путь, spec 011) — ночная
   добавка к notify, если arm-gone попал в интервал [ночь-2ч, ночь].
3. **`src/ping.ts`**: модель-ошибка (400/404/422) больше не зависит от
   кэшированных mode/model — цепочка фолбэков расширяется живыми моделями
   из `~/.pi/agent/models.json` (выбор по цене); рабочий фолбэк
   автоматически закрепляется в `state.ping.model` существующим
   `recordAutoResult`. Эскалация серии infra-отказов: не одна тихая
   пометка, а оповещение с периодом 6 ч, пока серия не прервётся.
4. **`src/nightplan.ts`**: `readActivePlan()` — обёртка над `readPlan()`:
   истёкший план = «нет плана» + однократная уборка файла под лок.

State-расширение: `state.sentry` — три отметки времени дедупа
(`lastNoArmNotifyAt`, `lastArmGoneNightNotifyAt`, `lastInfraNotifyAt`),
пишутся через `mutateState` (NFR-019-4). Все новые hooks — passive
observer, таймеры не добавляются (дозор живёт на существующих событиях:
ответы провайдера и sync-тик).

## 2. Ключевые решения

### D-001: где проверять «ночь без страховки»

Только на `after_provider_response` (каждый ответ модели ночью — включая
429-ошибки, которые тоже проходят через этот хук). Не на таймере: таймер
без ctx бесполезен для оповещений, а событие ответа гарантирует, что
(а) ночь действительно работает, (б) process жив, (в) notifier доступен.
Сторож «сессия мертва, но ночь зарегистрирована планом» уже есть — это
инвариант auto-rearm плана (spec 014); дозор закрывает другой разрыв:
ночь работает, а страховки НЕТ И ПЛАНА НЕТ.

### D-002: устранение мёртвой модели пинга (точная причина инцидента)

`sendPing` шаг 2 сегодня: `modelErr && mode0 === undefined && primary === PING_MODEL`.
`state.ping.model` закэширован как `openai/gpt-oss:20b`, `state.ping.mode`
как `json` → оба условия ложны → фолбэк не запускается никогда, 404
классифицируется infra, 23 отказа подряд за ночь. Решение: модель-ошибка
обрабатывается ВСЕГДА (независимо от кэша), цепочка попыток:
`primary → PING_FALLBACK_MODEL → модели провайдера по возрастанию цены
(максимум 3 штуки)`. Провайдер определяется по baseUrl из models.json,
совпадающему с cfg.baseUrl. Успешный фолбэк закрепляется существующим
механизмом (`recordAutoResult` пишет `res.model` в `state.ping.model`) —
самовосстановление без новых полей. Если ни одной модели у провайдера нет
— прежний infra-путь + FR-019-4 эскалация.

### D-003: чтение models.json в ping.ts

Новый помощник `readProviderModelIds(modelsFile, baseUrl): string[]`
(толерантный парс, без throw, кэш на 10 мин в module-scope переменной,
setPaths-хук для тестов). Выбор «самых дешёвых»: сортировка по
`cost.input`, при равенстве `cost.output`, срез 3. Чистая функция
`pickFallbackModels(list, exclude)` — тестируется без I/O.

### D-004: сводка /night-check — чистый рендер

`buildNightCheckReport(input): { text, verdict }` принимает уже прочитанные
данные (state, arms, plan, ping-подсостояние, локальное время строкой) —
никакого I/O внутри, полный юнит-тест. Вердикт — список разрывов:
`no-arm`, `window-low` (<30 мин до сброса или >80% окна израсходовано),
`ping-dead` (streak ≥ 10), `plan-expired-file`, `ok`.

### D-005: уборка протухшего плана

`readActivePlan()`: `readPlan()` → если `expiresAt < now` → `clearPlan()` +
`armslog` пометка «nightplan expired, файл удалён» (через существующий
логгер armslog.ts). Вызовы `readPlan()` в инварианте/отчётах переводятся
на `readActivePlan()`. Формат nightplan.json не меняется.

## 3. Data flow (дозор)

```
after_provider_response ──> nightsentry.checkNoArmGap({...}) ──pure──> gap?
   │                                                            │ да + дедуп прошёл
   │                                                            ▼
   │                                            mutateState(sentry.lastNoArmNotifyAt)
   │                                                            │
   └────────────────────────────────── notifier.notify("billing:night-no-arm", …)
```

Аналогично arm-gone: существующий переход в sync-пути →
`checkArmGoneNightGap(reason, nowLocal)` → ночное доп-оповещение
(не подавляется гашением spec 011 — это другой канал причины).

## 4. Risks / Trade-offs

- **Ложные срабатывания дозора** (вечерняя работа в 22:30 без взвода):
  это желаемое поведение — предупреждение, а не действие; дедуп 1/час
  держит шум низким.
- **Фолбэк-модель платная**: пинг — 1 токен; цена даже самой дорогой
  модели ничтожна; выбор самой дешёвой минимизирует.
- **Гонка уборки плана**: clearPlan под proper-lockfile — безопасно;
  повторное чтение после уборки вернёт null (файла нет).

## 5. Open Questions

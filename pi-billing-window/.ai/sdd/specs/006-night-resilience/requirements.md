# Spec 006 — night-resilience: stale-ctx задержка, межпроцессный дедуп, атрибуция armslog

> Status: Approved (оркестратор, 2026-09-27; поправка FR-201/US-2: дедуп per-armed-key)
>
> Source:
> - `diagnostics/2026-09-27-stale-ctx-missed-boundary.md` (спека 004) — инцидент:
>   доставка «продолжи» на 42 мин позже границы окна из-за `extension ctx is stale`.
> - `reports/stage0-baseline-distill.md` — дистиллят ночного базлайна 2026-09-27
>   (ключ TabDocLoad repeat=20, шторм рефайра 09-26, зомби-взвод, атрибуция).
> - Код: `src/index.ts`, `src/arms.ts`, `src/armslog.ts` (только анализ, без правок).

> не расширяется — атрибуция только аддитивно в деталях строки.

## Overview

Расширение представляет «продолжи» в чат на границе 2-часового биллинг-окна
провайдера wormsoft; ночь продолжается несколькими окнами подряд (repeat-режим).
Инвариант: доставка на границе, а не спустя десятки минут.

Инцидент 2026-09-27 нарушил инвариант: граница 18:26:07Z → доставка
`fire:send-ok` в 19:08:18Z (**+42 мин**). Спасал bounded-retry (D-204),
капитуляции не было; но ни одного `replacement:waiting`/`replacement:adopted` за
инцидент — путь переусыновления (D-201) не сработал, цепи `send-error:stale`
продолжались и после reload 19:03. Параллельно выявлены: дубли
`fire:reset-ready` на один сброс из разных процессов (D-203 дедуп модульный,
межпроцессного нет) и неатрибутивность armslog (`fire:send-ok`/`send-error` не
несут ключ сессии — night-mini вердикт формально FAIL только поэтому). Свежий
базлайн показал: субагент в родительском процессе создал дочернюю сессию,
расширение залогировало её `session-start` — глобальное состояние модуля
(currentCtx/epoch/таймеры) делится между сессиями одного процесса; гипотеза
«in-process субагенты инвалидируют ctx родителя без события replacement» требует
эксперимента (design).

Spec 006: ранняя диагностика + минимизация задержки доставки при stale-ctx;
межпроцессный дедуп сброса; аддитивная атрибуция armslog; наблюдаемость
субагент-инвалидации. Без изменения форматов и словаря событий.

## User Stories

- **US-1 (A, stale-ctx задержка)**. Как оператор ночного мониторинга я хочу,
  чтобы при устаревших ссылках окно либо быстро переуспыновило их, либо
  было видно в журнале, почему доставка отложена, — чтобы «продолжи» улетал на
  границе, а не через десятки минут.
  *Критерии приёмки:* replay инцидента (stale-ctx на границе + reload-переусыновление)
  даёт `fire:send-ok` в пределах одного backoff-шага от переусыновления; в журнале
  по инциденту-реплею есть различимый признак причины (epoch-mismatch) без новых
  слов событий.
- **US-2 (B, межпроцессный дедуп)**. Как верификатор ночного прогона я хочу,
  чтобы один сброс окна давал ровно один `fire:reset-ready` **на каждый
  взведённый ключ сессии** в журнале, какие бы живые процессы/хосты ни
  наблюдали сброс, — чтобы журнал не шумел (шторм 09-26
  ~157 строк) и вердикт был однозначен.
  *Критерии приёмки:* двухпроцессный тест и replay инцидента дают 1 строку
  `fire:reset-ready` на `lastResetAt` **на один взведённый ключ**; после
  рестарта процесса с живым флагом и перейдённой границей повторного fire того
  же сброса нет; **одновременно взведённые разные ключи каждый получают свой
  fire** (дедуп НЕ подавляет доставку между разными сессиями).
- **US-3 (C, атрибуция)**. Как аналитик я хочу, чтобы каждая строка armslog для
  fire-пути несла ключ сессии, процесс и эпоху, — чтобы вердикт ночи (PASS/FAIL,
  латентность, число дублей) выводился из журнала однозначно, включая night-mini,
  который сейчас FAIL формально.
  *Критерии приёмки:* строки `fire:reset-ready`/`fire:send-ok`/`fire:confirmed`/
  `send-error`/`send-error:stale` содержат аддитивный токен `key=…` (+pid/epoch);
  существующие `.includes()` подстроки тестов не нарушены; вердикт night-mini по
  журналу становится PASS при атрибуции.
- **US-4 (D, субагент-инвалидация, кандидат)**. Как оператор я хочу, чтобы смена
  владельца глобального состояния модуля (родитель↔дочерняя in-process сессия)
  оставляла след в журнале, — чтобы гипотеза инвалидации проверялась по факту, а не
  по догадке.
  *Критерий приёмки:* `session-start` сессии с ключом, отличным от владельца живого
  флага, фиксируется аддитивной деталью (сдвиг владельца контекста). Поведенческое
  изменение — за экспериментом (design), не входит в критерий приёмки этой итерации.

## Functional Requirements

### F1. Stale-ctx: ранняя диагностика и минимизация задержки (A)

- **FR-101 [Must / U]** — Когда армированный флаг переходит границу окна
  (`lastResetAt` продвинулся) в момент, когда `piApiEpoch !== sessionEpoch`
  (ссылки устарели), модуль должен зафиксировать это в деталях уже существующей
  строки (`fire:reset-ready` или первый `send-error:stale`) различимым для
  мониторинга аддитивным признаком `epoch-mismatch`, без введения нового слова
  события.
  *Verify:* unit-тест stale-эпохи ассертит токен `epoch-mismatch` в строке;
  мониторинг вычисляет признак по строке.
- **FR-102 [Must / A]** — После успешного переусыновления ссылок (эквивалент
  `replacement:adopted`) отложенный fire должен быть перерисован на следующем же
  retry-тике, и цепочка send-ошибок старой эпохи не должна мешать: задержка
  «граница → `fire:send-ok`» после переусыновления ≤ одного backoff-шага (≤5 мин),
  а не полной цепочки 5→10→20→40 мин как в инциденте.
  *Verify:* replay-тест инцидента: stale-ctx на границе → reload-переусыновление →
  `fire:send-ok` на первом же тике после переусыновления; в журнале нет
  продолжающихся stale-попыток старой эпохи после 19:03-эквивалента.
- **FR-103 [Should / A]** — Счётчик stale-попыток и его атрибуция должны быть
  привязаны к эпохе/процессу-отправителю, чтобы смешивание «1/6, 3/6, 4/6» из
  разных процессов (инцидент 19:07–19:27) было распознаваемым по журналу.
  *Verify:* тест атрибуции счётчика по эпохе в детали строки.

### F2. Межпроцессный дедуп сброса (B)

- **FR-201 [Must / U]** — Пока в профиле живы несколько extension-хостов/процессов,
  один сброс окна (`lastResetAt`) должен давать **не более одного**
  `fire:reset-ready` **на один взведённый ключ сессии** (at-most-once per
  (armedKey, lastResetAt)), при этом дедуп-маркер НЕ пишется в
  `arms.json`/`state.json` (форматы не меняются, D-004): допустим
  sidecar-маркер/лок-файл вне этих схем. Разные взведённые ключи друг друга НЕ
  дедуплируют: каждый ключ получает свой fire на общий сброс (важно для
  одновременных ночных выжигателей).
  *Verify:* двухпроцессный тест → 1 строка на сброс для одного ключа + два
  fire для двух одновременных ключей; replay 18:27 инцидента → 1, а не ×2/×3.
- **FR-202 [Must / A]** — После рестарта процесса с живым флагом и уже
  перейдённой границей окна дедуп должен переживать рестарт: повторный fire того же
  сброса не планируется.
  *Verify:* restart-тест → нет `fire:reset-ready` с той же меткой после рестарта.
- **FR-203 [Must / U]** — Дедуп не должен подавлять доставку: если держатель fire
  не может доставить (stale/send-error), маркер должен освобождаться (TTL/сброс),
  чтобы другой живой процесс мог доставить «продолжи»; капитуляция (D-204, никогда
  не молчать) сохраняется.
  *Verify:* takeover-тест: держатель stale → маркер снимается → второй процесс
  доставляет.
- **FR-204 [Should / U]** — Маркер/лок не удерживает процесс и не ускоряет пулл
  сверх существующих таймеров (unref, spec 003); защита от «застрявший лок» — TTL.
  *Verify:* тест exit-hygiene/`unref` на новый таймер.

### F3. Аддитивная атрибуция armslog (C)

- **FR-301 [Must / U]** — Каждая строка fire-пути (`fire:reset-ready`,
  `fire:send-ok`, `fire:confirmed`, `send-error`, `send-error:stale`,
  `replacement:waiting`/`replacement:adopted`, `capitulation:after-N`, `session-start`,
  `arm-seen`, `arm-gone`) должна нести аддитивную деталь с ключом сессии
  (`key=…`), идентификатором процесса/хоста (`pid=…`/`host=…`) и эпохой (`ep=…`)
  — без введения новых слов событий и без нарушения существующих `.includes()`
  подстрок в тестах.
  *Verify:* атрибуционный тест: новые строки содержат и старые подстроки, и новые
  токены; полный regress 10 сьютов 0 FAIL.
- **FR-302 [Must / A]** — После факта вердикт per-reset (лагентность доставки,
  число дублей, цепочка fire→send-ok→confirmed) должен выводиться из журнала
  исключительно по атрибутированным строкам; night-mini-вердикт по журналу должен
  становиться PASS при корректной атрибуции.
  *Verify:* верификатор на выгруженном инцидентном журнале (эмуляция атрибуции)
  даёт однозначный PASS/FAIL; сценарий night-mini (спека 004) без изменений по
  вердикту.
- **FR-303 [Should / U]** — Формат атрибутивных токенов фиксируется и
  документируется (единый префикс, порядок), машинно-парсится scenario_monitor'ом
  и night-monitor'ом без введения нового словаря.
  *Verify:* парсер мониторинга разбирает строки без правок схемы; юнит-тест формата.

### F4. Наблюдаемость субагент-инвалидации (D; только наблюдаемость)

- **FR-401 [Must / When]** — Когда в одном процессе приходит `session-start` с
  ключом сессии, отличным от ключа текущего владельца глобального состояния
  (currentCtx/epoch/арм), модуль должен аддитивно зафиксировать сдвиг владельца
  контекста (owner-shift), чтобы инвалидация родителя дочерней in-process сессией
  была диагностируема по журналу.
  *Verify:* тест с эмуляцией дочернего `session-start` → строка с деталью
  owner-shift/key; night-monitor умеет поднимать mismatch-флаг.
- **FR-402 [Should / кандидат, гейтится экспериментом]** — Изоляция глобального
  состояния по ключу сессии (чтобы дочерняя сессия не наследовала/не инвалидировала
  state родителя) НЕ формулируется как обязательное требование до эксперимента
  (Q-002): на этой итерации — только FR-401.
  *Verify:* нет (вне скоупа до эксперимента, см. Q-002).

## Non-functional Requirements

- **NR-1 [Must] Надёжность.** Механика «never fail silently» (D-204 bounded
  stale-retry 5→60 мин, капитуляция после 6) не регрессирует; новые пути не создают
  молчаливых смертей (armslog никогда не бросает — контракт `armslog.ts`).
  *Verify:* капитуляционные тесты 002 проходят без изменений; журнал пишется всегда.
- **NR-2 [Must] Наблюдаемость.** night-monitor/scenario_monitor вычисляют per-reset
  вердикт (лагентность граница→send-ok, дубли, цепочка) только по журналу;
  метрика лагентности доставки доступна машинно.
  *Verify:* мониторинг сценария из 004 обрабатывает новые аддитивные детали без
  правок; вердикт по атрибуции.
- **NR-3 [Must] Совместимость.** `arms.json`/`state.json`, словарь событий и логика
  checkAndReset/ticker не меняются; старые читатели/мониторинг работают (детали
  только аддитивны); базовая линия тестов сохраняется и расширяется (≥443 asserts,
  10 сьютов, 0 FAIL, добавочные новые сьюты).
  *Verify:* полный прогон `npx tsx tests/<имя>.test.mts` для всех 10 сьютов — 0 FAIL,
  число asserts ≥ 443.
- **NR-4 [Must] Производительность.** Новые лок/дедуп не добавляют пулл чаще
  существующих таймеров; новые таймеры/маркеры unref, не удерживают процесс (spec 003).
  *Verify:* exit-hygiene-тест на завершение процесса при применённом локе.
- **NR-5 [Should] Кроссплатформенность хранения.** Sidecar-лок/маркер для
  межпроцессного дедупа работает в любом расположении профиля (не только в каталоге
  сессии), устойчив к смерти держателя (TTL).
  *Verify:* тест с эмуляцией смерти держателя.

## Out of Scope

- Форматы `arms.json`/`state.json` (правила сброса windowMs, поля арма, `resetCount`,
  `lastResetAt`) — не меняются (D-004): дедуп-маркер только вне схемы (sidecar).
- Логика `checkAndReset` / ticker (`retryTick`, `armWatchdog`, `syncTick`) как таковая
  — не меняется; допустимые правки — только в части пути переусыновления/дедуп-маркера
  в рамках FR-102/FR-201…203.
- Протокол pi / ExtensionAPI — вне изменений; используется только переусыновление
  существующих ссылок (D-201) и существующий протокол событий.
- Словарь событий armslog — новые слова НЕ вводятся; атрибуция исключительно
  аддитивно в деталях строк (D-006).
- Механика сброса биллинг-окна (граница 2ч, windowMs, расчёт сброса) — вне
  расширения.
- Эксперимент по субагент-инвалидации (детерминированное воспроизведение,
  дизайн решения) — дело design-спеки; в рамках требований только наблюдаемость
  (FR-401), поведение — в Q-002.
- Смена целевого SLA/бизнес-правила окна — вне скоупа.

## Questions (открытые, существенные)

- **Q-001.** Почему `session_start reason=reload` не переснял piApi/eventBus так,
  чтобы следующая же попытка доставки прошла, и почему за инцидент ни одного
  `replacement:waiting`/`replacement:adopted` не записалось (путь D-201 фактически
  не сработал)? Это блокер для FR-102 — до ответа требование держится на replay-тесте.
- **Q-002.** Валидна ли гипотеза «in-process субагенты staled'ят ctx родителя без
  события session replacement» и как её детерминированно воспроизвести? От ответа
  зависит, превращается ли FR-402 (изоляция состояния по ключу сессии) из кандидата
  в Must.
- **Q-003.** Механизм межпроцессного дедупа: sidecar-лок vs маркер-файл vs
  файл-блокировка ОС; и как для FR-203 устроен takeover без роста латентности, если
  единственный держатель fire окажется stale-процессом.
- **Q-004.** Когда в pi нет стабильного идентификатора процесса/хоста — достаточно
  ли для FR-301 атрибуции ключ сессии + epoch (pid optional)? Что является каноничным
  `host`/`pid` для мониторинга night-mini?
- **Q-005.** Целевая латентность доставки на границе (FR-102: «≤ одного
  backoff-шага») — это обязательная Must-метрика или ориентир для мониторинга?
  Фиксировать ли её в night-monitor как порог вердикта?
- **Q-006.** Нужен ли «pending-hb» критерий жизни доставки (429-ночь убивает
  confirmed) для мониторинга, или это остаётся метрикой наблюдения без новых
  требований доставки?

## Decisions (решённые)

- **D-004** (ранее): форматы `arms.json`/`state.json` не меняются.
- **D-203** (ранее, 002): дедуп fire — модульный, in-memory `lastFiredResetAt`;
  межпроцессного нет (проблема B — предмет этой спеки).
- **D-204** (ранее, 002): bounded stale-retry 5→60 мин, капитуляция после 6 —
  сохраняется как «never fail silently».
- **D-005** (ранее, 005): fire-once-per-window — повтор в pending только после
  нового сброса; не регрессирует в 006.
- **D-006** (новая): словарь событий armslog НЕ расширяется; вся атрибуция —
  аддитивно в деталях строк (ключ/pid/эпоха); тесты, ищущие подстроки через
  `.includes()`, обязаны оставаться зелёными.
- **D-007** (новая): межпроцессный дедуп реализуется вне форматов state/arms
  (sidecar-маркер с TTL, unref), чтобы не нарушать D-004 и не менять ticker.
- **D-008** (новая): субагент-инвалидация на этой итерации — только наблюдаемость
  (FR-401); поведенческая изоляция состояния гейтится экспериментом (Q-002), а не
  форсируется в требованиях.

## Acceptance (сводно, проверяемо)

- Replay инцидента (stale-ctx на границе + reload-переусыновление): 1
  `fire:reset-ready` на сброс; `fire:send-ok` ≤ одного backoff-шага после
  переусыновления; признак `epoch-mismatch` в детали строки; нет продолжающихся
  stale-попыток старой эпохи после переусыновления.
- Двухпроцессный сценарий: один `fire:reset-ready` на `lastResetAt` на один
  взведённый ключ на всех процессах; два одновременных взведённых ключа дают
  два fire (по одному на ключ); рестарт не перефаривает тот же сброс; takeover
  при stale-держателе доставляет.
- Атрибуция: fire-строки несут `key=`/`pid=`/`ep=`; существующие `.includes()`
  подстроки целы; вердикт night-mini по журналу PASS при атрибуции.
- Наблюдаемость: `session-start` чужого ключа в процессе фиксирует owner-shift;
  мониторинг обрабатывает аддитивные детали без правок.
- Полный regress: `npx tsx tests/<имя>.test.mts` ×10 сьютов → 0 FAIL, asserts ≥ 443
  (+ новые сьюты/ассерты атрибуции, дедупа, replay-инцидента).

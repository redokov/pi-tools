# Spec 005 — fire-once-per-window (pending resend gated by window reset)

> Status: design
> Source: производственное наблюдение пользователя 2026-09-27: после
> `/settimer 54` + `/cont-after-reset` «продолжи» появляется в чате каждые 5
> минут вместо одного раза на границу окна.
> Scope: `src/index.ts` (retryTick pending-ветка), возможно `src/arms.ts`
> (константа-семантика). Форматы `arms.json`/`state.json` НЕ меняются (D-004).

## Problem

Pending-фаза (после успешной отправки «продолжи», до первого успешного ответа
провайдера) повторяет отправку каждые `RETRY_AFTER_FIRE_MS` (5 мин):

```ts
// src/index.ts, retryTick():
if (arm.phase === "pending") {
  const retryAfter = Math.max(arm.lastFireAt ?? 0, st?.last429At ?? 0);
  if (Date.now() - retryAfter < RETRY_AFTER_FIRE_MS) return;
  await fireContinue();
```

В ночном сценарии (429 заблокировал чат на всё окно) это заливает чат ~24
сообщениями «продолжи» за одно 2-часовое окно. Доказательство —
`~/.pi/agent/pi-billing-window-arms.log`, серия `fire:send-ok` для сессии
`01a0e327` в 14:35→14:40→14:45→14:50→14:55 (2026-09-27).

## Ожидаемое поведение (модель пользователя)

`/settimer 54` + `/cont-after-reset 10` → «продолжи» отправляется РОВНО ОДИН
РАЗ через ~55 мин (граница окна + grace 60с). Если чат заблокирован 429 —
следующая отправка не раньше следующего сброса окна (через ~2ч), и так каждое
окно, всего 10 отправок (repeat=10), пока флаг не исчерпается/снимется.

## Requirements

- **FR1** (одна отправка на сброс): после успешной отправки «продолжи»
  (phase `pending`) повторная отправка возможна только после НОВОГО сброса
  окна (`state.lastResetAt` продвинулся дальше сброса, на который была
  отправка). Никаких повторов «по таймауту» между сбросами.
- **FR2** (повтор после нового сброса): если в pending-фазе наступает новый
  сброс окна, выполняется ровно одна повторная отправка (подчиняется grace
  60с от нового сброса; дедуп D-203 действует как раньше).
- **FR3** (подтверждение): семантика `fire:confirmed` не меняется: первый
  успешный ответ провайдера после «продолжи» подтверждает флаг
  (repeat-1 / снятие). Подтверждение, пришедшее в любой момент между
  сбросами, по-прежнему снимает флаг немедленно.
- **FR4** (ошибки доставки): пути `send-error` / `send-error:stale` не
  меняются (bounded stale-retry 5→60 мин, капитуляция после 6) — они
  покрывают НЕУСПЕШНУЮ ОТПРАВКУ, а не отсутствие ответа.
- **FR5** (совместимость): форматы `arms.json`/`state.json` не меняются;
  новые таймеры не удерживают процесс (unref, spec 003); старые записи в
  arms.json работают после обновления без миграции.
- **FR6** (старый 5-мин интарвал): `RETRY_AFTER_FIRE_MS` остаётся как
  частота ПОЛИНГА условия в retryTick (дешёвый чек), но больше не является
  условием отправки.

## Acceptance

- Юнит/e2e: arm → reset → send-ok → (нет ответа) → +10 мин, +20 мин →
  отправок НЕТ; новый reset → ровно ОДНА отправка; ещё 10 мин без ответа →
  снова тишина.
- Live: сценарий A1 (сценарии 004) по-прежнему PASS; новый сценарий
  «429-ночь»: fire один раз на границу, между границами — ноль повторов.
- Полный регресс 9 сьютов: 0 FAIL (с поправкой тестов, кодировавших
  старую 5-мин семантику).

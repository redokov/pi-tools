# Feature: 013 — Ремонт history-файла с NUL-повреждением и молчаливое восстановление схемы

> Status: Draft
> Source: разбор инцидента с `~/.pi/agent/pi-billing-window-history.csv` (пользовательская постановка)
> Last Updated: 2026-10-24

## Overview

Файл истории `pi-billing-window-history.csv` (7.0 МБ) повреждён: файл начинается с блока из 5.8 МБ NUL-байтов (`\x00`), исходный заголовок `ts_iso,...` (13 колонок, UTF-8 BOM) уничтожен полностью, после NUL-блока идут валидные строки данных с 2026-10-14 (~7150 строк). Вероятная причина — крэш/потеря питания во время записи: NTFS добила начало файла нулями.

`ensureSchemaLocked()` при каждом append видит нераспознанную первую «строку» (NUL-блок) и пишет `console.warn` «unrecognized history header, skipping schema migration» — спам в каждом окне pi при каждом событии.

Фича включает две части: разовый ремонт существующего файла и постоянную способность `ensureSchemaLocked` молчаливо распознавать и чинить NUL-повреждение при его повторении.

## Business Context

- **Problem:** история биллинг-событий фактически потеряла заголовок и обросла 5.8 МБ мусора; каждое окно pi спамит warning при каждой записи.
- **Users:** пользователь pi-billing-window (все запущенные процессы pi, пишущие в общий файл истории).
- **Value:** сохранность аналитики по лимитам (calls/resets по проектам и по аккаунту), чистая консоль, устойчивость к будущим повреждениям.
- **Success signal:** warning исчез, файл корректно открывается, строки данных с 2026-10-14 не потеряны, append/trim работают как раньше.

## Goals

- Восстановить файл истории: срезать NUL-блок, вернуть актуальный HEADER, сохранить все строки данных.
- Сделать восстановление автоматическим и молчаливым: повторное NUL-повреждение чинится само, без warning.
- Прекратить спам warning об иностранном заголовке: не чаще одного раза на процесс.

## Non-Goals / Out of Scope

- Изменение формата CSV, набора колонок, схемы HEADER/LEGACY_HEADER.
- Изменение политики ретенции (`trimHistory`, RETENTION_DAYS).
- Восстановление уничтоженных NUL-блоком строк данных (старее 2026-10-14) — они невосстановимы.
- Работа с «иностранными» заголовками без NUL: чужие данные не трогаем (сохраняем warning, но без спама).
- Защита от повторного повреждения на уровне ОС/драйвера (UPS, fsync-политики).

## User Stories

### US-001: Пользователь перестаёт видеть спам warning

**As a** пользователь pi-billing-window
**I want to** чтобы при каждом событии биллинга в консоли не появлялся warning про unrecognized history header
**So that** консоль чистая и я не пропускаю реальные предупреждения

**Acceptance Criteria:**
- [ ] Для NUL-повреждённого файла warning не выводится вообще (молчаливый ремонт).
- [ ] Для файла с иностранным заголовком без NUL warning выводится не более одного раза на процесс pi.

### US-002: Файл истории починен и данные сохранены

**As a** пользователь, ведущий аналитику по лимитам
**I want to** чтобы файл истории снова начинался с валидного заголовка и содержал все уцелевшие строки данных
**So that** аналитика по проектам и по аккаунту не теряется

**Acceptance Criteria:**
- [ ] Файл начинается с `\uFEFF` + HEADER (13 колонок) + EOL.
- [ ] Все строки данных начиная с 2026-10-14 присутствуют в неизменном виде.
- [ ] NUL-блок удалён, размер файла уменьшается на ~5.8 МБ.

## Functional Requirements

### FR-001: Разовый ремонт существующего NUL-повреждённого файла — Must Have

WHEN выполняется разовый ремонт файла истории
IF файл начинается с блока NUL-байтов, за которым следуют строки данных
THE SYSTEM SHALL срезать ведущий NUL-блок, записать первой строкой актуальный HEADER (13 колонок) с UTF-8 BOM и сохранить все строки данных байт-в-байт
SO THAT файл снова соответствует текущей схеме без потери уцелевших данных.

EOL-стиль результирующего файла определяется по содержимому уцелевшей части (по аналогии с текущей логикой `ensureSchemaLocked`): CRLF-файл остаётся CRLF, LF-файл — LF.

### FR-002: Молчаливая авто-починка NUL-повреждения в ensureSchemaLocked — Must Have

WHEN `ensureSchemaLocked()` вызывается (внутри history-lock) и файл существует
IF первая «строка» файла содержит NUL-байты (`\x00`)
THE SYSTEM SHALL молча (без console.warn) выполнить ремонт: срезать NUL-префикс, подставить актуальный HEADER с BOM, сохранить остальные строки, определить EOL по содержимому
SO THAT повреждённый файл автоматически возвращается к рабочему состоянию при первом же append, без спама в консоли.

Обоснование безопасности: NUL-префикс — всегда следствие повреждения записи (крэш/потеря питания на NTFS), а не осознанный чужой формат, поэтому интерпретация однозначна.

### FR-003: Иностранный заголовок без NUL — warning без спама — Must Have

WHEN `ensureSchemaLocked()` видит первую строку, которая не равна HEADER, не равна LEGACY_HEADER и не содержит NUL-байтов
THE SYSTEM SHALL оставить файл без изменений (не трогать чужие данные) и вывести warning ровно один раз на процесс: повторные вызовы `ensureSchemaLocked` в том же процессе не предупреждают повторно
SO THAT поведение по отношению к чужим файлам сохраняется, но console-спам на каждый append исчезает.

Дедупликация warning выполняется под lock (флаг уровня модуля/процесса), чтобы гонка между одновременными append не дала двух предупреждений.

### FR-004: Идемпотентность и атомарность ремонта — Must Have

THE SYSTEM SHALL выполнять ремонт идемпотентно и атомарно: запись через временный файл + `renameSync` (тот же паттерн, что миграция LEGACY_HEADER), под уже существующим history-lock; ремонт никогда не бросает исключений (политика passive observer из history.ts: сбой = warn + false, биллинг и хост-процесс не затрагиваются).

Идемпотентность: повторный вызов на уже починенном файле — no-op (первая строка уже HEADER).

## Non-Functional Requirements

### NFR-001: Производительность

- Ремонт NUL-блока 5.8 МБ — одна операция «strip префикса + запись tmp + rename», без построчного парсинга/пересборки всего файла. Поведение append/trim и их производительность не меняются.

### NFR-002: Надёжность

- Крэш посреди ремонта оставляет либо старый (повреждённый) файл, либо новый (починенный), но никогда смесь (tmp + renameSync).
- Орфанных `.tmp`-файлов не остаётся (тот же finally-паттерн, что в существующей миграции).
- Все существующие гарантии history.ts сохраняются: appendHistory/trimHistory/ремонт никогда не бросают, ремонт идёт под lock, конкурентные процессы сериализуются как раньше.

### NFR-003: Наблюдаемость

- Молчаливый ремонт (FR-002) не пишет warning. Не запрещён один информационный журнал-уровень лога, но console-спам в окнах pi недопустим.

## User Experience Notes

- Пользователь не видит ремонта вообще: первое событие биллинга после повреждения тихо чинит файл.
- Единственное наблюдаемое изменение: исчезновение повторяющихся warning в консолях pi.
- Для файла с иностранным заголовком сохраняется прежняя семантика «не трогаем чужие данные», но предупреждение однократное.

## Constraints

- Файл общий для всех процессов pi — все операции только под history-lock (proper-lockfile), как сейчас.
- Кодовая база TypeScript, node:fs, никаких новых зависимостей.
- Политика passive observer обязательна: история никогда не ломает биллинг/тикер/хост-процесс.

## Decisions

### D-001: Разовый ремонт файла срезанием NUL-блока

**Decision:** Срезать ведущий NUL-блок, восстановить первую строку как актуальный HEADER (13 колонок) с BOM, все строки данных сохранить как есть. EOL определить по содержимому.
**Reason:** Заголовок уничтожен полностью и невосстановим; строки данных с 2026-10-14 валидны и ценны; срезание префикса — минимальное достаточное вмешательство.
**Source:** прямое пользовательское решение
**Impacts:** FR-001

### D-002: Молчаливая авто-починка NUL-повреждения в ensureSchemaLocked

**Decision:** `ensureSchemaLocked` распознаёт файл с ведущими NUL-байтами (первая «строка» содержит `\x00`) и чинит его молча (strip NUL-префикса + подстановка HEADER), без console.warn.
**Reason:** NUL-префикс — всегда следствие повреждения, не чужой формат; интерпретация однозначна, поэтому чинить безопасно и не о чём предупреждать.
**Source:** прямое пользовательское решение
**Impacts:** FR-002, US-001

### D-003: Иностранный заголовок без NUL — оставить как есть, warning без спама

**Decision:** Ветка warning для иностранного заголовка без NUL сохраняется (чужие данные не трогаем), но warning выводится не чаще одного раза на процесс, под lock.
**Reason:** Нельзя различить «чужой файл» и «наш файл с другим заголовком» — не трогаем; повторяющийся warning на каждый append — спам.
**Source:** прямое пользовательское решение
**Impacts:** FR-003, US-001

### D-004: Ремонт идемпотентен, атомарен и никогда не бросает

**Decision:** Ремонт: tmp + renameSync (как миграция LEGACY_HEADER), под существующим history-lock, исключения наружу не проскакивают (passive observer).
**Reason:** Тот же уровень гарантий, что у существующих операций history.ts; крэш посреди ремонта не должен усугублять повреждение.
**Source:** прямое пользовательское решение
**Impacts:** FR-004, NFR-002

## Questions

### Q-001: Как определять EOL-стиль у NUL-повреждённого файла?

**Status:** answered
**Answer:** По содержимому уцелевшей части (после NUL-блока), тем же способом, что и текущая `ensureSchemaLocked` для LEGACY-миграции: наличие `\r\n` → CRLF, иначе LF.
**Decision:** D-001

### Q-002: Отличать ли NUL-повреждение от иностранного заголовка с NUL?

**Status:** answered
**Answer:** Нет. Любая первая строка, содержащая `\x00`, трактуется как повреждение и чинится молча: NUL-префикс — всегда следствие повреждения, не осознанный формат.
**Decision:** D-002

## Glossary

- **NUL-блок:** непрерывная последовательность байтов `\x00` в начале файла — следствие обрыва записи на NTFS (аллокация добита нулями).
- **HEADER:** актуальный заголовок истории, 13 колонок `ts_iso,epoch_ms,kind,project,session,calls_in_window,reset_count,input,output,cache_read,cache_write,note,model`.
- **LEGACY_HEADER:** домодельный заголовок на 12 колонок; используется только для детекта и апгрейда старых файлов.
- **ensureSchemaLocked:** внутренняя функция history.ts, гарантирующая существование файла и актуальность схемы; вызывается под history-lock перед каждым append.
- **history-lock:** файловая блокировка (proper-lockfile), сериализующая доступ всех процессов pi к файлу истории.
- **passive observer:** политика history.ts — операции истории никогда не бросают исключений и не ломают биллинг/тикер/хост-процесс.

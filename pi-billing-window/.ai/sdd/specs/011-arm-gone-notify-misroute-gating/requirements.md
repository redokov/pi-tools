# Spec 011 — arm-gone notify, misroute-gating, confirmed-budget

## Header

- **Status:** requirements:approved (утверждено ТЗ пользователя от 2026-10-06 — аудит 2026-10-05, дефекты D1–D4)
- **Spec ID:** 011-arm-gone-notify-misroute-gating
- **Источники:** аудит ночи 2026-10-05 (`~/.pi/agent/pi-billing-window-arms.log`), README §8a, docs/handoff-006-night-resilience.md, spec 002/005/006/007/009/010

## Problem

Ночь 2026-10-05, флаг cont-after-reset (repeat=3, взведён 15:46), провайдер wormsoft, окно 2 ч:

1. сброс 19:17 — switchSession упал «ctx is stale», расширение сделало
   fall-through к обычной отправке и 5 раз отправило «продолжи» в ЧУЖИЕ
   сессии (misroute-отправки; запись в jsonl 2026-10-05T16-19-54…jsonl
   line 254, 20:40:39);
2. сбросы 21:17 / 23:17 — доставлены с опозданием 18–31 мин;
3. 23:35:51 флаг исчерпал repeat и исчез (arm-gone) БЕЗ уведомления — ночь
   осталась без автопродолжений, пользователь узнал об этом только утром.

Три продуктовых разрыва: доставка может уйти в чужой разговор; исчерпание
флага молчит; пользователь не видит «бюджет» оставшихся автопродолжений
до того, как флаг сгорит.

## User Stories

- **US-001 (D1):** Как пользователь, оставивший расширение работать ночью,
  я хочу получать уведомление, когда флаг cont-after-reset исчез/истёк
  (arm-gone), чтобы узнать о прекращении автопродолжений без чтения логов.
- **US-002 (D2):** Как пользователь, я хочу гарантировать, что «продолжи»
  никогда не уходит в чужую сессию, чтобы ночняя доставка не «терялась» в
  посторонних разговорах и не портила их.
- **US-003 (D3):** Как пользователь, я хочу при каждом подтверждённом
  автопродолжении видеть, сколько автопродолжений осталось, чтобы успеть
  перевзвести флаг до его исчерпания.
- **US-004 (D4):** Как сопровождающий репозиторий, я хочу актуальный
  SDD-индекс (specs 004–010, статусы 004–010), чтобы дашборд SDD отражал
  фактическое состояние проекта.

## Functional Requirements

### FR-011-1 (D1, Must) — arm-gone уведомление

WHEN sync-путь обнаруживает переход «флаг был → флага нет» (arm-gone:
запись исчезла из arms.json или истёк TTL), AND исчезновение НЕ вызвано
ручным снятием (`/cont-after-reset off`), AND НЕ покрыто только что
отправленным уведомлением капитуляции или подтверждения (дедуп, см.
FR-011-4), THE SYSTEM SHALL отправить уведомление через notifier.ts
(type `billing:cont-after-reset-arm-gone`) с полем reason
(`repeat-exhausted` | `ttl-expired`) SO THAT пользователь не узнаёт о
ночном простое только утром.

- reason = `ttl-expired`, когда у последней наблюдавшейся записи истёк
  `expiresAt` (8 ч);
- reason = `repeat-exhausted`, когда последняя наблюдавшаяся запись была
  в фазе `pending` с `repeat <= 1` (флаг снят подтверждением — в т.ч.
  другим процессом);
- прочие источники исчезновения (внешняя правка arms.json) попадают в то
  же уведомление с фактическим описанием в body.
- Ручное снятие (`off`) — уведомления НЕ отправляет (пользователь сам его
  сделал).

### FR-011-2 (D2, Must) — запрет fall-through-отправки при непрошедшем switch

WHEN fire-путь требует переключения на владельца (`fire:switch-needed`:
`lastSessionStartKey != ownerKey`), AND `switchSession` НЕ прошёл,
THE SYSTEM SHALL НЕ отправлять «продолжи» в этом раунде вообще, а
пропустить раунд с журналированием `fire:switch-blocked` и ждать
следующего retry-тика SO THAT misroute-отправка в чужую сессию становится
невозможной.

- Отправка «продолжи» выполняется только после успешного switch
  (в том же раунде или на последующих retry-тиках);
- поведение delivery-in-flight внутри grace (спека 005, инцидент T15) не
  меняется: гейтинг касается только новых попыток отправки, grace/pacing
  не сбрасываются;
- механики спеки 010 сохраняются: notify при первом switch-failed из-за
  мёртвого commandCtx; программный `switch-revive:cmd`
  (`/billing-status`) для восстановления commandCtx.

### FR-011-3 (D3, Must) — бюджет оставшихся автопродолжений

WHEN доставка «продолжи» подтверждена (`fire:confirmed`), THE SYSTEM
SHALL отправить уведомление «продолжи доставлен, осталось
автопродолжений: N», где N — оставшийся repeat после перевзвода, а при
N = 0 — фразу о том, что автопродолжения исчерпаны и флаг нужно взвести
снова (`/cont-after-reset N`) SO THAT пользователь видит бюджет до того,
как флаг сгорит.

- один notify на одно подтверждённое срабатывание (не чаще раза на окно).

### FR-011-4 (Дедуп, Must) — нет дублей уведомлений на одно событие

WHEN arm-gone-переход является следствием событий, о которых пользователь
уже уведомлён в том же процессе (капитуляция — свой notify; подтверждение,
снявшее флаг, — notify FR-011-3 с N=0), THE SYSTEM SHALL не отправлять
второе уведомление о том же событии (arm-gone остаётся в логе) SO THAT
пользователь не получает две нотификации об одном исчезновении флага.
Кросс-процессные подтверждения (флаг снят другим процессом) покрываются
FR-011-1 без дедупа.

### FR-011-5 (D4, Should) — SDD housekeeping

WHEN сопровождение SDD-каталога выполняется, THE SYSTEM SHALL содержать
`.ai/sdd/INDEX.md` со строками specs 004–010 и `.status`-файлы в
`004…010` по фактическому состоянию SO THAT дашборд SDD — источник
навигации по спецификациям.

## Non-Functional Requirements

- **NFR-011-1:** новые уведомления идут через существующий `notifier.ts`
  (D-205: никаких новых секретов/каналов); fire-and-forget, не бросают
  исключений в основные пути.
- **NFR-011-2:** таймерная гигиена (спека 003) не нарушается: новые пути
  не создают ref'нутых таймеров; все проверки — в существующих тиках.
- **NFR-011-3:** публичное поведение/CLI-контракты не меняются; новые
  лог-события (`fire:switch-blocked`) и notify-типы — только дополнения.
- **NFR-011-4:** тесты новых инвариантов — в стиле существующих сютов
  (`.test.mts`, mock pi/ctx как в lifecycle/session-isolation, notifier
  мокается перехватом fetch как в capitulation-тестах).

## Boundaries

- **In scope:** src/index.ts (arm-gone-переход, fire-путь, confirmed-ветка),
  тесты, SDD-каталог, README §8a, docs/EVENTBUS.md.
- **Out of scope:** деплой (отдельное подтверждение пользователя),
  переработка switchSession/adoptFreshRefs, изменение arms.ts-формата
  (кроме, при необходимости, read-only чтения полей), delivery-in-flight
  внутри grace (спека 005), пауза/капитуляция спеки 010.

## Questions

- **Q-001 (answered):** Дублируется ли D1 с D3 при исчерпании repeat в том
  же процессе? — Да, без дедупа; решение FR-011-4: при подтверждении,
  снявшем флаг (N=0), arm-gone-notify подавляется; reason
  `repeat-exhausted` остаётся для кросс-процессных/внешних снятий.

## Decisions

- **D-011-1:** reason-значения arm-gone — строго `repeat-exhausted` /
  `ttl-expired` (два канонических значения из ТЗ); внешний источник
  исчезновения описывается в body уведомления.
- **D-011-2:** misroute-механика (verifyDelivered, MISROUTE_MAX_ATTEMPTS)
  НЕ удаляется — она остаётся защитой для случаев, когда switch не нужен,
  а слот переехал (T15-смежные); гейтинг лишь перекрывает путь
  «switch нужен и не прошёл».

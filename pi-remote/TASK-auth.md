# Задача: аутентификация в pi-remote (один админ, пароль из .env)

## 1. Контекст

Проект: `c:/Tools/pi-remote` — однофайловый Node-сервер удалённого веб-терминала
для сессий AI-агента (pi). С телефона/планшета через Tailscale открывается
браузер, выбирается/создаётся «комната» = PTY-сессия на ноутбуке. Аутентификации
сейчас нет (README, п.5 принципа: «Без аутентификации — полагаемся на
приватность Tailscale»).

**Цель:** добавить аутентификацию. Один пользователь — администратор с паролем.
Пароль задаётся в файле окружения `.env` рядом с `server.js`. Флоу: при первом
заходе с мобильного/планшета — страница логина с полем пароля; после успешного
ввода — обычный интерфейс (выбор/создание комнат). Повторные заходы — без логина
(долгоживущая сессия в cookie).

## 2. Карта кода (проверено, экономь время)

- `server.js` — 842 строки, **намеренно pure ASCII** (комментарии и UI-строки на
  английском). Не нарушай это правило.
- Обработчик HTTP: колбэк `http.createServer` со строки ~134. Маршруты:
  `/health`, `/` (index), `/room/:name`, `/api/rooms` GET/POST,
  `/api/projects`, `/api/notify` (POST, токен `X-Notify-Token`,
  `PI_REMOTE_NOTIFY_TOKEN`), `/api/rooms/:name` GET/POST(restart)/DELETE,
  `/static/*`, fallback 404.
- WebSocket: `const wss = new WebSocketServer({ server })` (~строка 286),
  обработчик `wss.on('connection')` читает `?room=` из URL.
- Фронтенд встроен в server.js как template literals:
  `INDEX_HTML` (~строка 346, список комнат + форма создания + notify-WS на
  комнату `__notify_index__`) и `terminalPageHtml(name, cwd)` (~строка 504,
  xterm-терминал). Оба открывают WS на `/ws?room=...`.
- Зависимости: только `ws` и `node-pty` (package.json). **Новые npm-зависимости
  не добавлять** — .env-парсер и лимитер пишем руками (по ~15–25 строк).
- Лаунчеры: `start.bat`, `start-with-token.bat` (второй читает
  `PI_REMOTE_NOTIFY_TOKEN` из файла). Их менять не обязательно, т.к. сервер сам
  прочитает `.env`.
- Тесты (vanilla Node + CDP + ws, без playwright):
  - `test-e2e-rooms.cjs` — против **уже запущенного** сервера (порт из argv,
    по умолчанию 7681);
  - `test-e2e-mobile.cjs`, `test-e2e-delete.cjs` — **сами спавнят** сервер:
    `node server.js <port> cmd.exe C:\MyProjects 3600` (~строки 167/128);
  - `test-e2e.js`, `test-ws.js` — черновые/утилитарные.
- Git-репозитория в проекте нет.

## 3. Требования

Функциональные:
1. Пароль берётся из `.env` (ключ `PI_REMOTE_PASSWORD`) в корне проекта.
   Собственный мини-парсер: строки `KEY=VALUE`, `#`-комментарии, trim,
   реальный env **перекрывает** файл. Ничего не логировать из .env.
2. Если пароль не задан — **fail-closed**: сервер пишет понятную ошибку в
   консоль и завершается (exit 1). Создать `.env.example` с примером.
3. Форма логина: страница `/login` (встроенный HTML в server.js, стиль как у
   существующих страниц, UI на английском). Поле password + кнопка. После
   успеха — редирект на `?next=` (оригинальный путь; валидация: начинается с
   `/`, не `//`, нет scheme — против open redirect).
4. Неаутентифицированные: страницы (`/`, `/room/*`) → 302 на
   `/login?next=...`; API → 401 JSON `{error:'unauthorized'}`;
   WS-апгрейд → отклонять **до** handshake (401/403).
5. Исключения (без cookie-аутентификации): `/health`, `GET /login`,
   `POST /api/login`, `POST /api/logout`, `/api/notify` (остаётся со своим
   `X-Notify-Token`, machine-to-machine — cookie там нет).
6. Логаут: `POST /api/logout` удаляет сессию и cookie; на index — кнопка
   Logout (небольшая, не мешает мобильному UI).
7. Фронтенд: при закрытии WS с кодом 1008 / ошибке авторизации (и при 401 от
   fetch) — редирект на `/login`.

Безопасность (минимально достаточная, без велосипедов):
8. Сессии: `Map<token, {createdAt, lastSeen}>` в памяти; токен
   `crypto.randomBytes(32).toString('hex')`; cookie `pi_session`: HttpOnly,
   Path=/, SameSite=Lax, Max-Age = TTL. `Secure` — только если запрос https
   (`x-forwarded-proto` или socket.encrypted) — сервер работает по HTTP внутри
   Tailscale, Secure по HTTP сломает cookie.
9. TTL сессии скользящий, `PI_REMOTE_SESSION_TTL_HOURS`, по умолчанию 720
   (30 дней), чтобы с телефона не логиниться каждую неделю. Чистка протухших —
   раз в час по таймеру. Перезапуск сервера инвалидирует сессии — приемлемо.
10. Сравнение пароля — `crypto.timingSafeEqual` (хэшировать обе стороны до
    одинаковой длины, например sha256).
11. Rate limit на login: простой per-IP счётчик в памяти — 5 неудач → блок 60с.
12. `Cache-Control: no-store` на страницах и API с данными (комнаты).

## 4. Рекомендуемое решение по WS

Перевести на `WebSocketServer({ noServer: true })` + ручной
`server.on('upgrade', (req, socket, head) => ...)`: проверить cookie-сессию →
если нет, `socket.write('HTTP/1.1 401 Unauthorized\r\n\r\n'); socket.destroy()`;
если есть — `wss.handleUpgrade(req, socket, head, (ws) => wss.emit('connection', ws, req))`.
Парсинг cookie — простая функция из `req.headers.cookie`.

## 5. Шаги

1. `.env.example`, мини-парсер .env, fail-closed при отсутствии пароля.
   Проверка: сервер без пароля не стартует с внятной ошибкой; с паролем стартует.
2. Сессии + cookie + `POST /api/login` + `POST /api/logout` + страница `/login`
   (встроенный HTML) + редиректы/401 на защищённых маршрутах.
3. WS: noServer + проверка сессии на upgrade.
4. Фронтенд: Logout-кнопка в `INDEX_HTML`; обработка 401/1008 → редирект на
   `/login` (index и room-страница).

## 6. Тесты

- Новый `test-e2e-auth.cjs` (в стиле существующих, спавнит сервер на свободном
  порту с `PI_REMOTE_PASSWORD=test12345` в env процесса):
  1. `GET /` без cookie → 302 на `/login`;
  2. `GET /api/rooms` без cookie → 401;
  3. `POST /api/login` с неверным паролем → 401;
  4. с верным → 200/204 + Set-Cookie `pi_session`;
  5. `GET /api/rooms` с cookie → 200;
  6. WS без cookie → отказ апгрейда (expect error на connect);
  7. WS с cookie → соединение устанавливается;
  8. `POST /api/logout` → после него API снова 401;
  9. `POST /api/notify` с корректным `X-Notify-Token` (поднять сервер с этим
     env) работает без cookie;
  10. rate limit: 5 неверных паролей подряд → 429/403 до истечения блокировки.
- Обновить `test-e2e-mobile.cjs` и `test-e2e-delete.cjs`: в env спавна добавить
  `PI_REMOTE_PASSWORD`, после запуска сервера залогиниться через CDP-браузер
  (открыть `/login`, ввести пароль, сабмит, дождаться редиректа) — это заодно

## 8. Вне объёма (не делать)

Много пользователей, смена пароля из UI, HTTPS/терминация TLS, CSRF-токены
(достаточно SameSite=Lax + JSON-POST), хэширование пароля в хранилище
(пароль живёт в `.env` в открытом виде — это осознанно), БД/файловое хранилище
сессий.

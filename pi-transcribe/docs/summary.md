# ТЗ: сохранение саммари транскрибации в `out/<filename>-sum.md`

## Контекст

Проект `c:/tools/pi-transcribe` — это конвейер подготовки аудио/видео и отправки в API
транскрибации wormsoft. Сейчас в `out/` сохраняются только сырые результаты
транскрибации (`*.txt`, `*.srt`, `*.vtt`, `*.json`). Содержимое этих файлов используется
дальше «в чате» — но **нигде не сохраняется итоговое саммари**, которое готовит LLM-агент
по результату транскрибации.

Нужно ввести правило/процедуру, по которой агент после транскрибации **всегда** сохраняет
саммари в ту же папку `out/` в виде `<filename>-sum.md`, чтобы:

- саммари можно было потом открыть в любом Markdown-редакторе / на гитхабе;
- оно лежало рядом с исходной транскрибацией и было привязано к конкретному файлу;
- имя файла однозначно говорило, что это «суммари от такого-то исходника», и не путалось
  с сырыми `*.txt`.

## Что сделано сейчас

- `scripts/transcribe.py` умеет класть результат в `out/<base>.<ext>` (`txt`, `srt`,
  `vtt`, `json`, `verbose.json`). Это **сырая** транскрибация, не саммари.
- В `AGENTS.md` и `docs/workflow.md` описано, что после транскрибации агент «может
  обработать результат дальше» (в т.ч. сделать саммари) — но **без явного требования
  сохранять саммари в файл**.
- В `out/` уже лежат примеры сырых результатов: `video1668379769.txt`, `video1931585114.txt`.

## Цель

Добавить в проект **обязательный шаг «сохранить саммари»**, чтобы:

1. После успешной транскрибации агент читал полученный `out/<name>.<ext>` (обычно `.txt`).
2. Готовил по нему саммари.
3. **Сохранял саммари в `out/<name>-sum.md`** (т.е. рядом с исходной транскрибацией,
   формат `<filename>-sum.md` — например, `video1668379769-sum.md`).
4. Использовал это саммари в ответе пользователю (выводил в чат кратко, со ссылкой на
   полный файл).

## Требования к агенту

### Когда запускать

- Шаг сохранения саммари обязателен после **любой** успешной транскрибации:
  - при ручном цикле (подготовка → transcribe.py → саммари);
  - при вызове `/transcribe` / `/transcribe-gigaam` (расширение `pi-transcribe`) — там,
    где раньше саммари шло только в чат, теперь нужно дополнительно писать его в файл.
- Если пользователь явно попросил `--no-summary` или сказал «без саммари» — файл не
  создавать.
- Если транскрибация упала — саммари не сохранять, файл не создавать.

### Что подавать на вход

- Вход — файл `out/<name>.<ext>` (по умолчанию `*.txt` — обычный текстовый результат
  `text`).
- Если в `out/` лежит только манифест и `*.json`/`*.verbose.json` без `.txt` — сначала
  извлечь из JSON поле `text` (для `verbose_json` ещё есть смысл учитывать
  `segments[].text`/`start`/`end`, чтобы при необходимости давать таймкоды).
- Для `*.srt` / `*.vtt` — суммари готовить по тексту реплик, таймкоды в саммари
  выносить в отдельный раздел «Ключевые моменты (таймкоды)» (см. ниже).
- Если `out/<name>.txt` уже существует и непустой — использовать его; не переписывать
  заново, не скачивать заново.

### Что считать саммари

Структура файла `out/<name>-sum.md` — следующая (один файл, Markdown, UTF-8):

```markdown
# Саммари: <basename>

- **Исходник**: `<basename>.<source_ext>` (например, `video1668379769.mp4`)
- **Транскрибация**: `out/<basename>.txt`
- **Язык**: <ru|en|…> (если известно)
- **Модель**: <gigaam|whisper-large|…> (если известно)
- **Дата саммари**: <YYYY-MM-DD HH:MM локального времени>
- **Объём исходника**: <длительность из manifest.json или N символов / N слов>

## TL;DR
<2-5 предложений: что за встреча/запись, главный вывод, какое решение или итог>

## Ключевые темы
- <тема 1>
- <тема 2>
- …

## Подробно по темам
### <тема 1>
<краткое описание, 2-5 предложений>
### <тема 2>
…

## Решения / действия
- [ ] <действие 1>  *(если были явные задачи/договорённости)*
- [ ] <действие 2>

## Открытые вопросы
- <вопрос, который остался без ответа>
```

Допускается сокращать/дополнять разделы под содержимое (например, для короткой записи
можно не выделять «Решения»). Главное — чтобы был хотя бы блок «TL;DR» + одна из
расширенных секций.

### Имя файла

- Строго `<basename>-sum.md`, где `<basename>` — это **stem исходного видео/аудио**,
  т.е. имя файла из `inbox/`, **до** расширения.
- Для манифеста `out/<basename>.manifest.json` — `<basename>` берётся так же из `stem`
  манифеста.
- Не использовать префиксы `summary_`, `sum_`, `s_` и т.п. — только `-sum.md`.
- Если файл `out/<basename>-sum.md` уже есть — **перезаписать** (свежее саммари
  актуальнее). Не плодить `*-sum-1.md`, `*-sum-2.md`.

### Куда сохранять

- В ту же папку `out/`, что и сырая транскрибация (т.е. **рядом** с `*.txt`).
- Полный путь: `c:/tools/pi-transcribe/out/<basename>-sum.md`.
- Не сохранять в `inbox/`, в корень проекта, в `docs/` — только в `out/`.

### Кодировка / формат

- UTF-8, без BOM.
- Перевод строк LF (`\n`), не CRLF (для совместимости с гитхабом и большинством
  редакторов). Если транскрипт был в CRLF — это нормально, главное чтобы **новый файл
  саммари** был LF.
- Кодировка заголовка Markdown — без `---` сверху, начинается с `# Саммари: …`.

## Доработка: имя саммаризованного файла по содержанию + дата

Актуальная правило (pi-transcribe, TZ-summary-name.md): саммаризованный файл получает
название **по содержанию транскрипции** — CamelCaseWords (слова в CamelCase, без пробелов
и спец-символов, русский или англий — по содержанию) — плюс дата `YYYY-MM-DD` в конце,
 перед расширением:

- Пример: `meeting.mp4` → `out/MeetingPlanVersions-2026-08-31.md` ( вместо старого
  `out/meeting-sum.md`).
- Каталог: `out/` (рядом с транскрибацией).
- Название генерирует агент-суммаризатор (он читает транскрипт и знает содержание).
- Файл уже может существовать (manifest reuse) — перезаписать по правилам, новые
  версии не создавать.
- Структура файла: «# Саммари: <basename>» + метаданные + TL;DR + «## Ключевые темы» +
  «## Подробно по темам» + «## Решения / действия» + «## Открытые вопросы» (см. выше).
- Кодировка: UTF-8 без BOM, перевод строк LF.


## Если саммари большое


НЕ печатайте транскрипцию или саммари в чат — только краткий итог.


- НЕ генеририуйте повторные Cyrilic- блоки: если Cyrillic- слово повреждено (�), не продолжайте копирование — переформулируйте и продолжайте.
- Write-вызов с огромным файлом превышает лимит output tokens — сохраните файл несколькими write-вызовами.


- Сохраните файл несколькими небольшими write-вызовами: write первой части, затем edit-дополнения по разделам.
- В чат — краткий итог (2–4 предложения) и путь к файлу.


## Имя саммаризованного файла


Формат: `out/<ProjectName><CamelCaseWords>-<YYYY-MM-DD>.md`.


- **1) имя проекта** — на русском, CamelCase
- **2) название по содержанию** — CamelCaseWords на русском
- **3) дата** YYYY-MM-DD в конце перед расширением


В имени НЕ должны быть: пробелы, подчёрки, дефисы, спец-симв.олы, символ � (U+FFFD) и любые непечатаемые символы — только буквы и цифры. Если буква не распозналась — переформулируйте имя на чистый русский.
